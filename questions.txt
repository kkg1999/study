 - Implement a connection pool.
 	1. Its a connection pool of 1000 - 2000 connections 
	2. The developers who will use your interface can request for a connection. 
	3. If there is a free connection in the pool, you give the connection to the requester.
	4. Once the connection is used by the developer, they can return back the connection to the pool Or close the connection.
	5. If the connection is closed, create a new connection and keep it in the pool. The count of the connections should be maintained throughout.
	6. A Connection will have 3 states - FREE, BLOCKED, CLOSED. 
	7. If the connections in the pool are exhausted, and requests for connections are coming from developers, keep an in-house mechanism to a default timeout and reject the request if there is no connection being freed within that default timeout. If you get a connection within the time, return the connection.

 - I had to implement a ride sharing system. Some condtions were there.
    Multiple passengers can request rides, and the available drivers take them on their journeys.
    However, each passenger must be assigned exactly one driver, and no driver can take more than one passenger at a time.
    If all drivers are busy, passengers must wait until one becomes available. Passengers get assigned to the first available driver.
    Drivers are reassigned immediately after they complete a ride.
    Guarantee that exactly one driver serves each passenger.
    No two passengers are assigned the same driver simultaneously.
    Ensure that multiple passengers and drivers can interact concurrently without any conflicts.
    The platform needs to ensure thread safety and prevent race conditions.
    I had to use ExecutorService, Manual time outs to simulate the system.
    BlockingQueues, Concurrent Data structures to make it thread safe.
    This was more of a design based plus algo question.

Salesforce heavily tests for "multi-tenant" and enterprise-scale thinking, especially for SMTS and LMTS roles.
Workflow / Rule Engine: Designing a system that evaluates business rules dynamically without hardcoding them (metadata-driven).
Role-Based Access Control (RBAC): Designing a permission system that securely handles users, roles, and granular data access.
CRM Object Model: Designing core entities (Accounts, Leads, Contacts, Opportunities) with flexible, extensible relationships.

Essential Design Patterns
- Strategy Pattern: Essential for varying algorithms (e.g., Fare calculation in cab booking, Pricing rules in a shopping cart).
- State Pattern: Critical for state machines (e.g., Elevator movement, Connection Pool lifecycle states).
- Observer Pattern: Core for asynchronous events and triggers (e.g., Notification delivery).
- Factory Pattern: For decoupling the creation of complex objects or varying implementations.

Salesforce interviewers consistently introduce multi-threaded follow-ups or base the entire question (like the Connection Pool) on resource scarcity.
	- Thread Safety: Preventing race conditions and deadlocks using C++ (std::mutex, std::unique_lock, std::shared_mutex) or Java (ReentrantLock, synchronized).
	- Producer-Consumer Coordination: Mastering C++ std::condition_variable or Java BlockingQueue for task orchestration.
	- Lifecycle Management: Understanding thread pools (Java ExecutorService or custom C++ worker pools) and safely handling thread starvation or timeouts.
